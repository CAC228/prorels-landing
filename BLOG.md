# Блог ПроРельс

Блок на главной, `/blog` со всеми статьями и отдельные статические страницы `/blog/[slug]`. Визуальный референс — https://zdprog.ru/blog/oshibki-v-marketinge-prodazh-vsp и предоставленный скриншот карточки. Сохранены логика карточек, тёмная шапка статьи, оглавление и акцентные заметки; цвета, шрифты и контент адаптированы к ПроРельс.

Опубликованы пять текстов: Р65 новые/с хранения/б/у; состав КБ-65 на шпалу; подготовка заявки; сравнение предложений; доставка. Две технические статьи добавлены по брифу заказчика: с источниками, таблицами, схемой КБ-65 и формой для запроса расчёта. Тексты референса не копировались. Именные эксперты, выдуманные сертификаты, цены, отзывы и гарантии не добавлялись.

## Добавление статьи

Контент хранится в `src/content/articles.ts`, без CMS и базы данных. Добавьте объект в `articles`:

- `slug` — уникальный адрес латиницей, цифрами и дефисами;
- `status` — `published` для публикации или `draft` для скрытого черновика;
- `title`, `description`, `category` — заголовок, описание и рубрика;
- `publishedAt`, `updatedAt` — настоящие даты публикации и содержательного изменения в формате `YYYY-MM-DD`;
- `intro`, `sections`, `takeaway` — вступление, разделы и итог;
- `catalogCategory` — необязательный slug категории в prorelsa.ru.
- `callout` — необязательные `title` и `text` для формы в конце статьи;
- `sources` — ссылки на использованные документы/каталоги с пояснениями; они также выводятся как `citation` в BlogPosting.

В каждом разделе нужны уникальный `id`, `title` и `paragraphs`. Можно добавить `list`, `note`, `table`, текстовый `template` и `diagram: 'kb65'`. Схема условная, не монтажный чертёж. HTML и скрипты в контенте не исполняются. `id` служит якорем в оглавлении; `takeaway` зарезервирован для итогового блока. Время чтения рассчитывается по объёму текста. Авторство указано как «Материал ПроРельс», без фиктивных людей и должностей.

Порядок массива задаёт порядок карточек. На главной показываются первые три опубликованные статьи, в связанных материалах — до двух других. Черновики исключаются из карточек, страниц, социальных изображений и sitemap общим селектором. Неизвестный или скрытый адрес возвращает 404. Планирование публикации по будущей дате не реализовано: будущий текст нужно держать в `draft`.

После изменения контента выполните `npm test`, `npm run build`, перезапустите приложение. Не меняйте slug уже опубликованной статьи без плана перенаправления со старого адреса. При смене даты публичного запуска проверьте `publishedAt`; `updatedAt` меняйте только вместе с содержанием, а не при каждой сборке.

## SEO

Все тексты, оглавления и ссылки находятся в HTML, полученном от сервера. Статьи имеют собственные title/description, canonical, Open Graph `article`, Twitter-карточку, изображения 1200×630, BlogPosting и BreadcrumbList JSON-LD. Индекс блога имеет CollectionPage и ItemList. В JSON-LD используются те же тексты и даты, что видит читатель.

До выбора домена сохраняется общий режим noindex. При отсутствии `SITE_URL` не выводятся придуманные canonical и идентификаторы страниц. После задания `SITE_URL` и `SITE_INDEXABLE=true` в sitemap входят главная, `/blog` и опубликованные статьи; `lastmod` статьи берётся из `updatedAt`. Реальная индексация зависит от размещения и обхода поисковиками.

Изображения для соцсетей создаются при сборке, без внешних запросов. Кириллический Golos Text загружен из Google Fonts: https://fonts.googleapis.com/css2?family=Golos+Text:wght@600&display=swap. Локальный TTF и лицензия SIL OFL находятся в `public/fonts`. Обычные страницы продолжают использовать существующие локальные WOFF2.

## Docker и текущая схема размещения

Next.js генерирует эти страницы при сборке. Переменные только в `docker run` или `docker compose` **не изменят уже созданные метаданные**. Для существующего GitHub Actions workflow задайте Repository Variables `SITE_URL` (HTTPS-домен лендинга) и `SITE_INDEXABLE` (`true` только для публичного запуска). Workflow передаст их как build args. Без переменных образ по умолчанию остаётся noindex.

Для ручной сборки:

```sh
docker build --build-arg SITE_URL=https://your-landing-domain.ru --build-arg SITE_INDEXABLE=true -t prorels-landing .
docker run --rm -p 5000:5000 prorels-landing
```

Адрес в примере необходимо заменить на фактический. Порт контейнера 5000 сохранён. `.dockerignore` исключает локальные зависимости, сборку, Git и `.env` из контекста образа.

## Проверки

```sh
npm run lint
npm test
npm run build
npm run typecheck
npm start
# Во втором терминале:
npm run verify:seo
```

Проверка HTTP проходит по индексу и всем статьям: полный HTML, один H1, уникальные метаданные, оглавление, ссылки на другие материалы, canonical, JSON-LD, sitemap, PNG-превью и реальные 404. Параметры `VERIFY_URL`, `VERIFY_SITE_ORIGIN`, `VERIFY_INDEXABLE` задают ожидаемые результаты проверки; приложение ими не настраивается.

GitHub Actions `check.yml` выполняет эти проверки для двух независимых сборок: без домена (noindex) и с тестовым доменом (index). Тестовый `landing.example.org` используется только для проверки строк в метаданных и не является адресом публикации.
